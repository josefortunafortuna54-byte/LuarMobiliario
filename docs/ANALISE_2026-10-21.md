## 1. O que está bem (para não mexer)

O trabalho de segurança do backend é **genuinamente bom** e não deve ser desfeito:

- Policies por role em `properties`/`lands` (`002`): `update own or admin`, `admin delete` apenas.
- `users` com `read own or admin` (`007`) — **PII (email/phone) corretamente protegida**.
- View `users_public` (`021`) para leitura pública sem PII — evita o bug do ecrã de mensagens.
- Triggers `prevent_role_change` (`006`) e `prevent_self_verification` (`021`) — impedem auto-escalação de privilégios.
- `moderation_log` para auditoria de ações de moderação.
- `get_user_role()` como `SECURITY DEFINER` — a checagem de role nunca corre com privilégio do cliente.
- Índices trigram GIN (`029`) para `ilike '%x%'` — as pesquisas não fazem full scan.
- Secrets fora do repositório: `--dart-define`, `.env` ignorado, `set_admin_passcode.sql` também ignorado (`luar_company/.gitignore:64`).

**Conclusão:** o RLS é sólido e deve servir de base. O problema de autorização está **na camada de UI**, não na base de dados.

## 2. Achados CRÍTICOS

### C1 — A autenticação de admin é um PIN de 6 dígitos usado como password do Supabase

**Evidência**
- `luar_company/lib/screens/auth/admin_login_screen.dart:132` — a validação exige **exatamente 6 dígitos** (`length != 6` → `passe6Digitos`).
- `luar_company/supabase/set_admin_passcode.sql:15` — `v_pass := '123456'`, inserido em `auth.users` com `crypt(v_pass, gen_salt('bf'))`.

**Problema**
O segredo de administração tem um espaço de **1 000 000 de combinações** e é aceite diretamente pelo endpoint de autenticação do Supabase. O rate-limit por IP do Supabase é real, mas 10⁶ é um espaço pequeno para um atacante paciente ou distribuído — e o valor `123456` é o primeiro a ser testado em qualquer tentativa. Não é um problema de armazenamento (o ficheiro está corretamente gitignored): é um problema de **desenho do segredo**.

**Impacto** — acesso total à plataforma: users,-properties, lands, bookings, reports, moderação.

**Correção**
1. Substituir o PIN por password real (política mínima de 10 caracteres) **ou** 2FA TOTP para o role `admin`.
2. Se o PIN tiver de sobreviver por UX, torná-lo um **segundo factor** (password + PIN), nunca o factor único.
3. Rate-limit/lockout explícito no caminho de admin (a app já tem a branch `muitasTentativas` — `admin_login_screen.dart:101` — mas depende do limite genérico do Supabase).
4. Substituir o valor real por placeholder no script (`v_pass := 'ALTERE-ME'`), mantendo a instrução de rodar.

### C2 — O gate de role é inconsistente: agentes entram no painel admin e veem o inventário global

**Evidência — o gate diverge entre ecrãs**

| Local | Regra | Resultado |
|---|---|---|
| `admin_login_screen.dart:79` | `role != 'admin' && role != 'agent'` | **agente entra** |
| `admin_dashboard.dart:30` | `agent \|\| admin` | agente entra |
| `admin_properties.dart:35` | `agent \|\| admin` | agente entra |
| `admin_lands.dart:34` | `agent \|\| admin` | agente entra |
| `admin_bookings.dart:32` | `agent \|\| admin` | agente entra |
| `admin_users.dart:33` | `role != admin` → sai | só admin ✅ |
| `admin_reports.dart:31` | `role != admin` → sai | só admin ✅ |

**Evidência — o ecrã não é filtrado por agente**
- `admin_properties.dart:46` → `context.read<PropertyProvider>().loadProperties()` → `property_repository.fetchProperties()` (`property_repository.dart:84-102`) **sem filtro `agent_id`** → devolve **todos** os anúncios da plataforma.
- `admin_properties.dart:363-379` mostra **Editar** e **Apagar** em *cada* linha.
- `property_form_screen.dart` — `grep` de `agent_id|currentUser|user.id` → **zero ocorrências**. Não há verificação de posse.

**Problema**
Um agente autenticado obtém: o inventário completo de todos os anúncios da plataforma, as métricas globais (`admin_dashboard` → `loadStats()`/`loadAnalytics()`: totais de users/properties/lands, preço médio, mais vistos) e a **capacidade de abrir o formulário de edição de anúncios de outros agentes**.

**Nota importante e verificada**
O RLS **não é furado**: `Properties: update own or admin` + `Properties: admin delete` (`002_rls_role_based_policies.sql:76-85`) impedem a escrita cruzada. **Não há exfiltração de dados nem alteração indevida de anúncios.** O dano é (a) divulgação de informação fora do âmbito do role e (b) UX partida — o agente vê botões que o servidor vai recusar, e recebe em troca o erro cru do Postgres (ver C3).

**Correção**
1. Unificar o gate num único helper (`canAccessAdminPanel(role)`, `canManageAllListings(role)`) usado pelos 7 ecrãs.
2. Decidir o produto: `admin_users`/`admin_reports` são admin-only → os restantes devem ser também (agents já têm `my_listings_screen`).
3. Se os ecrãs de properties/lands ficarem acessíveis a agentes, **escopar por `agent_id`** e esconder Editar/Apagar quando `agent_id != currentUser.id`.
4. Adicionar verificação de posse no `property_form_screen` (abrir outro anúncio deve ser read-only, ou redirecionar).

### C3 — `ErrorMapper` e a hierarquia de `Failure` são código morto; o `e.toString()` cru vai para a UI

**Evidência**
- `core/utils/error_mapper.dart` (58 linhas) + `core/errors/app_failure.dart` (36 linhas) existem e estão bem desenhados.
- `grep -rn "error_mapper|ErrorMapper|mapError" lib/` → **1 hit, a própria definição**. Zero consumers.
- Todos os providers fazem `_error = e.toString()`: `admin_provider.dart:41,57,72,89,125,138`; `search_provider.dart:321,345`; `property_provider.dart:47`; `auth_provider.dart:36,57,63,94,100,118,146,164`; etc.

**Problema**
O utilizador vê literalmente:
```
PostgrestException: new row violates row-level security policy for table "properties"
```
Isto (a) expõe detalhe do schema, (b) não é traduzido apesar de a app ter PT/EN completo, (c) não é acionável — não há indicação de "tenta outra vez" nem de que a operação foi bloqueada por permissões.

**Correção**
1. Ligar `ErrorMapper.toMessage(e)` em todos os `catch` dos providers/repositories.
2. Distinguir `PostgrestException` com código RLS (42501 / `PGRST301`) → mensagem "Sem permissão para esta ação" (traduzida).
3. Guardar a `Failure` (não a String) no estado, para a UI poder decidir entre *retry* e *mensagem terminal*.

## 3. Achados de prioridade ALTA

### H1 — O dashboard de admin carrega tabelas inteiras para a memória

`admin_repository.dart:11-23` (`fetchStats`) faz `select('id')` sobre `properties`, `lands`, `users`, `messages` — **traz todas as linhas só para as contar**. `admin_repository.dart:68-79` (`fetchAnalytics`) traz **todas** as linhas de `properties`, `lands`, `users` e `bookings` e agrega em Dart (`:86-138`).

Complexidade: **O(total de linhas)** por abertura do dashboard, em rede e em RAM. Com 10 000 anúncios são ~10 000 linhas + 10 000 users + todas as marcações.

> A migration `026_analytics_views.sql` chama-se "analytics views" mas **não cria nenhuma view** — apenas a coluna `views` e a RPC `register_listing_view`. O nome promete o que não existe.

**Correção**: RPCs de agregação no Postgres (`admin_stats()`, `admin_analytics()`) ou views materializadas; no cliente usar `select('id', {count: 'exact'})` para as contagens simples.

### H2 — `fetchUsers()` não pagina
`admin_repository.dart:26-35` → `select()` sem limite → **todos** os utilizadores registados. `admin_users.dart` (897 linhas) filtra no cliente. Com 50 k utilizadores o ecrã fica inutilizável e o payload é enorme.

**Correção**: paginação por cursor + filtro de pesquisa no servidor (`ilike` sobre `name`/`email`, com índice trigram).

### H3 — Contagens que puxam tabelas inteiras
`property_repository.dart:343-359` — `countByAgent` e `countAvailableByAgent` fazem `select('id')` e contam em Dart. O mesmo existe em `land_repository`.

**Correção**: `.select('id', {count: 'exact'})`.

### H4 — `update()` de anúncio é destrutivo e não atómico
`property_repository.dart:172-202`: faz `DELETE` de **todas** as linhas de `property_images` e `property_videos`, e só depois re-insere. Se a inserção falhar, **o anúncio fica sem media**. Também descarta edições concorrentes e gera escrita em massa desnecessária.

**Correção**: diff (inserir novos / remover explicitamente removidos) ou `upsert` por URL; wrap em RPC transacional.

### H5 — A ordenação dos resultados só funciona na primeira página (bug visível)
`search_provider.dart:70-74` (`setSort`) e `:406-442` (`propertyResults`/`landResults`) ordenam **em Dart, sobre o que já está carregado**. O servidor ordena sempre por `created_at DESC` (`property_repository.dart:250,325`).

Resultado: "preço ascendente" reordena os 20 itens da página 1, mas a página 2 continua em `created_at` e ao carregar mais a lista **muda de ordem**. O utilizador vê a ordenação "saltar".

**Correção**: o `orderBy`/`ascending` já existem como parâmetros no repositório —ligar `setSort` ao servidor e recarregar (redefinindo a paginação).

### H6 — Três implementações paralelas e divergentes de pesquisa, por entidade
`property_repository.dart`:
- `_applyFilters` based em `Map` (`:31-82`)
- `searchAdvanced` com parâmetros nomeados (`:232-329`)
- `search()` legado (`:214-230`) — **não pede `property_videos`** e usa um conjunto diferente de campos

`land_repository.dart` replica as três (`:23-60`, `:~185-200`, `:~210-276`).

≈250 linhas duplicadas e a divergir (o `search()` legado não devolve vídeos — bug latente se algum dia for usado num ecrã com vídeo).

**Correção**: um único builder de query partilhado (`ListingQuery` + `applyTo(PostgrestFilterBuilder)`), parametrizado por tabela/campos.

### H7 — `land_repository` é um clone de `property_repository`
Corpos de `switch` idênticos em `_applyFilters`; cadeias de filtros idênticas em `searchAdvanced`. Qualquer correção num tem de ser replicada no outro.

**Correção**: extrair a camada de query partilhada (ver H6).

### H8 — O contador de visualizações não tem deduplicação
`registerView` é chamado em cada abertura do detalhe (`property_provider.dart:102`, `land_provider.dart:100`) → `register_listing_view` incrementa sempre. Conta: o próprio dono a ver o anúncio, e cada reabertura. O painel "mais vistos" (`admin_repository.dart:118-138`) fica inflado e não significa nada.

**Correção**: tabela `listing_views` com `UNIQUE (listing_id, device_id)` + TTL, ou contador com janela temporal.

### H9 — A mudança de role não é auditada
`admin_repository.setUserVerified` (`:50-56`) grava em `moderation_log`. `admin_repository.updateUserRole` (`:37-39`) **não** — sendo a ação de **privilégio mais alto** do painel.

**Correção**: gravar `moderation_log` em toda a mutação de role/verified.

### H10 — `register_guest_client` é escrita anónima com `SECURITY DEFINER` e sem rate-limit
`013_guest_registration.sql:22-68`: cria uma linha em `public.users` (email sintético `@guest.luar`) a partir de `anon`, com `GRANT EXECUTE ... TO anon` (`:67-68`). Sem limite de chamadas → vector de spam/inundação de contas.

Já está assinalado como não resolvido em `docs/SECURITY_AUDIT.md:51` ("Adicionar rate-limit, validação telefone, prevenir spam").

**Correção**: rate-limit por IP no Edge Function / trigger, ou exigir autenticação para marcar visitas (o `register_guest_client` só é usado por `booking_repository.dart:91`).

### H11 — Os links partilhados são becos sem saída (gap funcional de maior valor)
`core/utils/deep_links.dart:5-9` gera `https://luarcompany.ao/properties/{id}` e `.../lands/{id}`. O payload de partilha (`property_detail_screen.dart:278-284`, `land_detail_screen.dart:180`, `discover_screen.dart:850`) envia exatamente esse URL.

**A landing page não tem router.** `index.html` + `js/main.js` + `js/featured.js`: `grep -rn "pushState|popstate|location.pathname|hashchange"` → **zero resultados**. O link partilhado no WhatsApp abre a homepage, e o anúncio não é alcançável.

Em Angola o WhatsApp é o canal principal de distribuição. Cada partilha de anúncio — a principal alavanca de crescimento do produto — está a morrer num link morto.

**Correção**: router client-side na landing page que lê `location.pathname`, faz `fetch` do anúncio na Supabase (chave anon + RLS de leitura pública) e renderiza a ficha, com `history.replaceState` e fallback para a app.

### H12 — O Discover só mostra imóveis e não tem pull-to-refresh
`discover_screen.dart` — sem `RefreshIndicator`, sem integração de terrenos (o `DiscoverProvider` suporta ambos). O feed é o ecrã com maior potencial de retenção e está incompleto.

## 7. P0 — Implementado (2026-10-21)

As três acções do P0 foram implementadas. Estado do gate de qualidade:

### P0-1 — Password real no lugar do PIN de 6 dígitos

| Antes | Depois |
|---|---|
| PIN de 6 dígitos usado directamente como password Supabase | Password real, mínimo de 10 caracteres |
| `admin_login_screen.dart` aceitava `agent` no login de admin | Login de admin é **exclusivo de `role = admin`** |

- `AppConstants.adminPasswordMinLength = 10` é a fonte única do mínimo.
- A política está em `Validators.adminPassword()` (`core/utils/validators.dart`),
  não num método privado do ecrã: assim é testável sem instanciar o widget e
  fica disponível para o resto da app.
- Teclado do campo passou de `TextInputType.number` para `TextInputType.text`
  (a password deixou de ser numérica).
- L10n: `passe6Digitos` → `passeMinCaracteres`; `passeAcesso`/`passeHint`/
  `insiraPasse`/`insiraEmailPasse`/`passeIncorreta` passes a falar em
  "palavra-passe" (PT/EN). `flutter gen-l10n` regenerou os três ficheiros
  `app_localizations*.dart`.
- `supabase/set_admin_passcode.sql` deixou de ter credenciais em texto claro
  (`'123456'`, email real). Passa a exigir `SUBSTITUIR_*` e **aborta** se a
  password tiver < 10 caracteres. O ficheiro continua git-ignored.

> **Acção operacional do utilizador (obrigatória):** a password real do
> administrador tem de ser definida executando o script actualizado no SQL
> Editor do Supabase (ou via Supabase Auth). A password actual `123456`
> deixa de ser aceite pela app.

### P0-2 — Gate de role unificado

Novo `luar_company/lib/core/utils/permissions.dart` com uma única fonte de
verdade:

| Função | Regra |
|---|---|
| `canAccessAdminPanel(role)` | `role == admin` |
| `canManageAllListings(role)` | `role == admin` |
| `canCreateListing(role)` | `agent` ou `admin` |
| `ownsListing({role, agentId, currentUserId})` | admin é dono de tudo; agente só do seu |

- Os **6 ecrãs administrativos** (`admin_dashboard`, `admin_properties`,
  `admin_lands`, `admin_bookings`, `admin_users`, `admin_reports`) usam
  `denyUnlessAdmin(...)` — o gate deixou de estar duplicado em 7 sítos com
  regras divergentes.
- O menu **Admin** do `profile_screen.dart` passou a ser exclusivo de
  `role = admin` (antes um agente via para o dashboard global).
- `property_form_screen.dart` e `land_form_screen.dart` ganharam verificação
  de posse: só o dono (ou o admin) abre o formulário de edição. O RLS já
  recusava a escrita; a UI deixou de oferecer a acção.

**Detalhe de implementação que importa:** o `Navigator.pop()` é um no-op
quando o ecrã é a rota inicial — o `pop` não substitui o bloqueio. Por isso
o guard faz as duas coisas: faz `pop` **só se** `navigator.canPop()`, e o
ecrã passa a desenhar `AccessDeniedView` (novo widget) em vez do painel
administrativo. Sem isto, o painel continuava visível para o agente
(confirmado por probe antes/depois da correcção).

### P0-3 — `ErrorMapper` ligado a toda a app

- Os **55** `_error = e.toString();` nos 12 providers passaram a
  `_error = ErrorMapper.toMessage(e);`. Já não há nenhum `toString()` cru
  nos providers (`formatters.dart` mantém os seus, que são legítimos).
- `app_failure.dart` ganhou `PermissionFailure`.
- `ErrorMapper.isPermissionError()` detecta violação de RLS por **código**
  (`42501` insufficient_privilege, `PGRST301`) e por **mensagem**
  (`row-level security`, `permission denied`, `not authorized`, ...). A
  `postgrest` 2.8.0 não expõe `statusCode` na excepção, por isso a
  detecção é por código + mensagem.
- Uma violação de RLS passa a mostrar *"Sem permissão para esta operação.
  Contacte o administrador."* em vez de expor o SQL do Postgres ao utilizador.

## 8. Nota metodológica

- Todos os achados têm evidência `ficheiro:linha` verificável no estado actual do repositório.
- A hierarquia RLS foi reconstruída **por ordem de aplicação das migrations** (001→029), porque várias policies são substituídas por versões posteriores (`007` substitui a `006` em `users`, por exemplo). Conclusões sobre a policy em vigor foram confirmadas contra a última migration que a toca.
- O gate de qualidade foi executado localmente: `flutter analyze` sem issues, 522 testes verdes.
- **Duas hipóteses iniciais foram refutadas durante a verificação e não constam como achados**: (a) a credencial de admin **não** está no histórico Git — `luar_company/.gitignore:64` exclui `supabase/set_admin_passcode.sql`; (b) a PII de `users` **não** está exposta — a policy `read own or admin` de `007` substitui a `public read` de `006`.
